# Simulation correctness rules

These rules are non-negotiable. If a change would violate one, stop and raise it.

## Random numbers
- All randomness comes from named, seeded streams (`packages/core/src/rng.ts`).
  Never call `Math.random()` in core code.
- Stream seed = f(master seed, stream name, replication index). Separate streams per
  stochastic input (e.g. `arrivals`, `service`) so that common random numbers stay
  synchronized when other parameters change.
- In the queue model, each customer's service time is drawn **at arrival, in arrival
  order**, from the `service` stream. This keeps customer n's service requirement
  identical across scenarios that share a seed.

## Run phases (queue model)
- Initial state: empty and idle at t = 0.
- Warm-up: [0, W). Measurement window: [W, H]. Arrivals are generated only on [0, H].
- Measured cohort: customers who arrive in [W, H].
- End of run ("drain-cohort"): after H, no new arrivals; the simulation continues
  until every cohort customer has departed. Cohort customers are never excluded
  because they were still in the system at H. The count still waiting or in service
  at H is reported as `censoredInQueueAtHorizon` and `censoredInServiceAtHorizon`.
- Time-averaged metrics (L, Lq, utilization, max queue) integrate only over [W, H].
- Every metric has exactly one basis, stated in its description:
  - **cohort**: customers arriving in [W, H], with full waits included through drain;
  - **window**: integrals or counts over [W, H] only.
  Never combine bases inside one metric (`costPerHour` was fixed for this in queue.mmc@1.1.0).
  See docs/validation/reproducibility.md.
- "No observations" is NaN, never 0. Serialization encodes it as {"$nonFinite":"NaN"}.
- Little's law over a finite window has boundary terms. Verify both:
  1. The exact sample-path identity: area of N(t) over [W, H] equals the sum of each
     customer's sojourn overlap with [W, H].
  2. The asymptotic relation L ≈ λ̂·W̄, with the tolerance justified by run length.

## Time-varying schedules (queue.daypart)
- Arrivals with piecewise-constant rates are generated by an exact time change: Exp(1)
  draws from the `arrivals` stream are inverted against the cumulative rate, so rate
  boundaries and zero-rate intervals are handled exactly. Service times are still drawn at
  arrival, in arrival order.
- A staffing decrease never interrupts service. Staff above the new level finish their
  current customer and then leave; paid on-duty time is max(capacity, busy).
- At closing, arrivals stop and block-6 staff keep serving until the system is empty,
  then capacity is 0 until the next opening. Any backlog carries over.
  From queue.daypart@0.2.0 a staff member leaves after closing as soon as no one is waiting
  for them (paid after-close time = busy time), the same rule as a mid-day decrease.
- Blocks are half-open [start, end). An arrival that lands exactly on the end of its block is
  processed before that boundary (0.2.0), so it meets its own block's staffing.
- Paid time is reported in three parts that must add up: scheduled (Σ staff × 2 h),
  overrun (finishing a customer after a decrease) and after-closing. All at one hourly rate.
- queue.daypart@0.1.0 stays registered and unchanged so its results reproduce. Never change a
  released version's behaviour; add a version.
- Warm-up must be 0 and the horizon a whole number of days; every customer is drained.
- The stationary special case must equal queue.mmc sample path by sample path. Never use
  Erlang C to validate a genuinely time-varying case.

## Statistics
- Report the mean, sample SD, standard error and a Student-t confidence interval across
  **independent replications**, not across correlated customers within one run.
- t quantiles are computed numerically from the t distribution, not from a lookup table.
- When several hypothesis checks form one benchmark family, control the family-wise
  error (Bonferroni) and state the number of checks.

## Tests
- Never weaken a test, loosen a tolerance, change a seed, or discard replications
  to make a failing test pass. A failing benchmark is a finding; report it.
- Benchmarks are seeded, so they are deterministic. A failure is reproducible evidence.
- Common random numbers do not guarantee variance reduction. Measure it; never assert
  it as universal. Report the ratio Var(D) / (Var(A) + Var(B)) for each comparison; a
  test model with anti-correlated outputs (ratio ≈ 2) proves the report can show an increase.

## Scenarios and comparisons
- A scenario's `id` is its identity; its `fingerprint` is its content. Results carry a separate `resultHash`.
- Completed scenarios are immutable. Changing them requires a fork.
- A version mismatch must never be reported as an identical replay.
- One-at-a-time sensitivity uses the baseline seed and settings, changing exactly one parameter per run.
  Interaction = combined − Σ effects, per replication. It is not a unique attribution.
